# Phase 16 — Accounts & Identity Architecture

**Status:** Design  
**Prerequisite:** Phases 10A–10D complete  
**Scope:** Architecture specification only — no implementation  

---

## 1. Overview

ClearSignal currently operates as a single-user intelligence platform. Every entity
that will eventually belong to a user — watchlists, portfolios, delivery preferences,
briefings, notifications — already carries a nullable `user_id VARCHAR(64)` column.
NULL today means "global / system-owned." Phase 16 makes that field non-nullable by
introducing a canonical `users` table, an authentication layer, and ownership rules.

The design goal is **additive and non-breaking**: existing NULL rows are claimed by
a system user on migration, the first real user inherits that data on sign-up, and
no existing service logic needs to change until Phase 16 ships.

### What changes

| Layer | Before | After |
|---|---|---|
| Identity | `user_id = NULL` (implicit global) | `user_id` always references `users.id` |
| Auth | No auth (open API) | JWT bearer tokens via Supabase Auth |
| API | All endpoints public | Authenticated middleware on user-scoped routes |
| Data | One watchlist, one portfolio | Per-user watchlists and portfolios |
| Delivery | Delivered to "global" | Delivered to authenticated user_id |

### What does not change

- The portfolio intelligence pipeline (Phases 10A–10D) — services remain user_id-aware via the existing nullable column; routing is the only new layer
- The analysis engine (Phase 9A–9G) — session_id-based analysis continues unchanged; user_id is additive context
- Shadow mode on all delivery — stays active until explicitly promoted

## 2. Identity Model

### 2.1 Core data model

```
users
├── id                VARCHAR(36) PK  — UUID, generated by auth provider
├── email             VARCHAR(320) UNIQUE NOT NULL
├── email_verified    BOOLEAN DEFAULT FALSE
├── created_at        TIMESTAMPTZ NOT NULL
├── updated_at        TIMESTAMPTZ NOT NULL
├── last_sign_in_at   TIMESTAMPTZ
├── is_active         BOOLEAN DEFAULT TRUE
└── account_type      VARCHAR(20) DEFAULT 'individual'
      -- 'individual' | 'team_member' | 'institutional' | 'system'
```

```
user_profiles
├── user_id           VARCHAR(36) PK FK → users.id
├── display_name      VARCHAR(200)
├── timezone          VARCHAR(60)  DEFAULT 'UTC'
├── locale            VARCHAR(10)  DEFAULT 'en'
├── avatar_url        VARCHAR(500)
├── onboarding_step   VARCHAR(60)  DEFAULT 'pending'
│     -- 'pending' | 'watchlist' | 'portfolio' | 'briefing' | 'complete'
├── onboarding_completed_at TIMESTAMPTZ
├── created_at        TIMESTAMPTZ NOT NULL
└── updated_at        TIMESTAMPTZ NOT NULL
```

```
user_settings
├── user_id            VARCHAR(36) PK FK → users.id
├── briefing_time_utc  INTEGER DEFAULT 8      -- hour (0–23) for morning brief
├── quiet_hours_start  INTEGER DEFAULT 22
├── quiet_hours_end    INTEGER DEFAULT 7
├── delivery_channel   VARCHAR(20) DEFAULT 'in_app'
│     -- 'in_app' | 'email' | 'push'
├── digest_enabled     BOOLEAN DEFAULT TRUE
├── theme              VARCHAR(20) DEFAULT 'system'
│     -- 'light' | 'dark' | 'system'
├── created_at         TIMESTAMPTZ NOT NULL
└── updated_at         TIMESTAMPTZ NOT NULL
```

**Design notes:**

- `users.id` is the provider-assigned UUID from Supabase Auth. This avoids generating
  a second UUID and keeps the auth provider as the identity source of truth.
- `user_profiles` and `user_settings` are 1:1 with `users`, created on first sign-in.
  They are separate tables so the identity record stays thin and profile queries
  are clearly separated from authentication state.
- `account_type = 'system'` is reserved for the single SYSTEM_DEFAULT_USER row that
  holds all pre-Phase-16 NULL-owned data during the migration window.

### 2.2 Relationship to existing user_id fields

Every existing `user_id VARCHAR(64) nullable=True` column becomes a soft FK to
`users.id`. The column type (VARCHAR(64)) already accommodates the UUIDs Supabase
Auth generates. No column type changes are required.

Tables with user_id that need ownership claims after migration:

| Table | user_id nullable? | Migration target |
|---|---|---|
| `thesis_versions` | yes | SYSTEM_DEFAULT_USER |
| `memory_entries` | yes | SYSTEM_DEFAULT_USER |
| `personalized_insights` | yes | SYSTEM_DEFAULT_USER |
| `watched_tickers` | yes | SYSTEM_DEFAULT_USER |
| `user_delivery_prefs` | yes | SYSTEM_DEFAULT_USER |
| `digest_batches` | yes | SYSTEM_DEFAULT_USER |
| `notifications` | no (already required) | Already scoped; remains as-is |
| `portfolios` | yes | SYSTEM_DEFAULT_USER |
| `portfolio_positions` | via portfolio | Inherited from portfolio row |
| `portfolio_insights` | via portfolio | Inherited from portfolio row |

Tables that remain genuinely global (not user-scoped):

| Table | Reason |
|---|---|
| `cross_exposures` | Company-level signal, not user-owned |
| `dossier_*` tables | Company intelligence, platform-wide |
| `ticker_memory` | Per-ticker aggregate, not per-user |
| `historical_analogs` | Curated reference library |
| `scheduled_jobs`, `job_locks`, `job_runs` | Platform infrastructure |
| `delivery_ledger` | Delivery record; scoped via target_key |
| `theme_clusters` | Platform-level cross-ticker signal |

## 3. Authentication

### 3.1 Evaluation

| Method | Pros | Cons | Fit |
|---|---|---|---|
| Email/password | Familiar; user controls credential | Password storage burden; bcrypt overhead; reset flows | Medium |
| Magic link | Zero password storage; low friction; phishing-resistant | Requires reliable email delivery; session is link-lifetime | **High** |
| Google OAuth | One-click; high trust; no password | Google dependency; user needs Google account | **High** |
| GitHub OAuth | Good for technical users | Too niche for financial platform | Low |
| SMS/TOTP 2FA | Strong second factor | Not a primary method; adds friction | Future only |
| SAML/SSO | Required for enterprise | Complex; over-engineered for Phase 16 | Phase 16.2+ |

### 3.2 Recommended architecture: Supabase Auth

**Recommendation:** Supabase Auth as the identity provider, with magic link as the
primary sign-in method and Google OAuth as the secondary.

**Why Supabase Auth:**

1. **Designed for PostgreSQL.** The `auth.users` schema lives in the same database,
   eliminating a separate identity service. The `users.id` FK to `auth.users.id`
   is a direct PostgreSQL FK with no external call required.

2. **Magic links + OAuth out of the box.** No custom auth code to write or audit.
   Magic links require only an SMTP relay (Render provides one via SendGrid/Resend).

3. **JWT tokens.** Supabase issues signed JWTs. The existing FastAPI backend adds
   one middleware function (`verify_jwt`) — no new auth service, no session DB table.

4. **Row-level security (RLS) ready.** When Teams/Institutional accounts arrive,
   PostgreSQL RLS policies can enforce data isolation without application-layer
   changes. Supabase Auth's JWT `sub` claim maps directly to `users.id`.

5. **Free tier.** Up to 50,000 MAU on the free plan. No cost until scale.

**Alternative if self-hosted is preferred:** Auth.js (NextAuth.js) on the frontend
with a custom JWT issuance endpoint on the backend. More control, more code.
Not recommended for Phase 16 given Supabase's simpler operational profile.

### 3.3 Authentication flow

```
Sign-up / Sign-in (magic link)
──────────────────────────────
1. User enters email → POST /auth/magic-link (Supabase client)
2. Supabase sends one-time link to email (expires 1 hour)
3. User clicks link → Supabase validates OTP → issues JWT + refresh token
4. Frontend stores access_token in memory (not localStorage)
   Stores refresh_token in httpOnly cookie (not accessible to JS)
5. Frontend includes Authorization: Bearer <access_token> on every API call
6. FastAPI middleware verifies JWT signature using Supabase public key (JWKS)
7. Verified `sub` claim becomes request.state.user_id

Sign-in (Google OAuth)
──────────────────────
1. User clicks "Sign in with Google"
2. Redirect to Supabase OAuth flow → Google consent screen
3. Supabase exchanges code → issues JWT + refresh token (same as above)
4. Identical token handling from step 4 onward

Token refresh
─────────────
Access token TTL: 1 hour
Refresh token TTL: 30 days (sliding)
Frontend SDK handles refresh automatically on 401
```

### 3.4 JWT structure

```json
{
  "sub": "uuid-of-user",           ← becomes user_id in all DB writes
  "email": "user@example.com",
  "role": "authenticated",
  "aud": "authenticated",
  "exp": 1234567890,
  "iat": 1234567890,
  "app_metadata": {
    "account_type": "individual"   ← copied from users.account_type at sign-in
  }
}
```

The `sub` claim is a stable UUID. It is the value stored in every `user_id` column.

### 3.5 Session security

- Access tokens stored **in memory only** on the frontend (lost on tab close; re-obtained via refresh token)
- Refresh tokens stored in **httpOnly, Secure, SameSite=Strict cookies** — inaccessible to JavaScript
- Supabase Auth handles token rotation on refresh (old refresh token invalidated on use)
- Logout invalidates the refresh token server-side via Supabase `signOut()`

## 4. Authorization

### 4.1 Principle

Every user-scoped route checks `request.state.user_id` (injected by JWT middleware)
against the `user_id` column of the resource being accessed. No resource is accessible
without a verified user_id. Resources owned by SYSTEM_DEFAULT_USER are readable by
any authenticated user until explicitly claimed (see §5.2).

### 4.2 Ownership rules by entity

**Portfolios**

```
portfolios.user_id = request.user_id         (hard ownership)
portfolio_positions → owned via portfolio_id (no separate check needed)
portfolio_insights  → owned via portfolio_id (no separate check needed)
```

A user can only read, modify, or delete portfolios where `portfolios.user_id`
matches their JWT `sub`. Cross-user portfolio sharing is out of scope for Phase 16
(see §7.3 Teams).

**Watchlist**

```
watched_tickers.user_id = request.user_id    (hard ownership)
```

Each user has their own independent watchlist. Tickers on the global/system watchlist
are read-only references until claimed at onboarding (see §6.2).

**Delivery preferences**

```
user_delivery_prefs.user_id = request.user_id
```

Each user has their own preferences. The SYSTEM_DEFAULT_USER preferences are used as
defaults when creating a new user's preference row (copy-on-first-access).

**Inbox (notifications)**

```
notifications.user_id = request.user_id      (already enforced; user_id NOT NULL)
```

No change needed. The inbox is already user-scoped.

**Briefing sessions**

```
briefing_sessions.user_id = request.user_id
```

Session records created before Phase 16 (user_id = NULL) belong to
SYSTEM_DEFAULT_USER and are visible only to admins after migration.

**Digests**

```
digest_batches.user_id = request.user_id
```

Global digest_batches (user_id = NULL) claimed by SYSTEM_DEFAULT_USER at migration.

**Analysis results (thesis, memory, dossier)**

Analysis results are currently scoped by `session_id`. In Phase 16 they gain
`user_id` ownership: results for `session.user_id = request.user_id` are readable.
Dossier/company data remains global (company intelligence is platform-level).

**Delivery ledger**

The delivery ledger `target_key` field already encodes recipient context. For user
deliveries, `target_key = user_id`. No schema change; the ledger is read by admins
only, never directly by users.

### 4.3 API protection tiers

```
Public (no auth required)
  GET  /health
  GET  /healthz
  POST /auth/*         (Supabase client handles; backend never sees credentials)

Authenticated (JWT required)
  GET  /portfolios
  POST /portfolios
  GET  /portfolios/{id}
  GET  /watchlist
  POST /watchlist
  GET  /notifications
  GET  /briefing
  GET  /admin/portfolio-status   (admin role required — see below)
  GET  /admin/delivery-status    (admin role required)
  POST /analyze                  (user_id injected as context)
  POST /ask

Admin (JWT + account_type='system' or custom role claim)
  GET  /admin/*
```

Admin routes are protected by an additional `require_admin` dependency that checks
`app_metadata.role = "admin"` in the JWT. Admin users are provisioned manually via
Supabase dashboard; there is no self-service admin promotion.

## 5. Migration Strategy

### 5.1 Overview

The migration has three phases:

```
Phase 16.0 — System user seed (runs at deploy, before any real user signs up)
Phase 16.1 — User sign-up + data claim (runs on first real user onboarding)
Phase 16.2 — Backfill & cleanup (runs after all active users have claimed)
```

### 5.2 Phase 16.0 — System user seed

On first deploy of Phase 16 code, the startup lifespan:

1. Creates one row in `users`:
   ```
   id           = SYSTEM_DEFAULT_USER_ID  (a fixed, well-known UUID constant)
   email        = "system@clearsignal.internal"
   account_type = 'system'
   email_verified = true
   ```
   This is idempotent — skipped if the row already exists.

2. Runs a single UPDATE to claim all NULL `user_id` rows:
   ```sql
   UPDATE watched_tickers         SET user_id = SYSTEM_DEFAULT_USER_ID WHERE user_id IS NULL;
   UPDATE portfolios              SET user_id = SYSTEM_DEFAULT_USER_ID WHERE user_id IS NULL;
   UPDATE user_delivery_prefs     SET user_id = SYSTEM_DEFAULT_USER_ID WHERE user_id IS NULL;
   UPDATE digest_batches          SET user_id = SYSTEM_DEFAULT_USER_ID WHERE user_id IS NULL;
   UPDATE thesis_versions         SET user_id = SYSTEM_DEFAULT_USER_ID WHERE user_id IS NULL;
   UPDATE memory_entries          SET user_id = SYSTEM_DEFAULT_USER_ID WHERE user_id IS NULL;
   UPDATE personalized_insights   SET user_id = SYSTEM_DEFAULT_USER_ID WHERE user_id IS NULL;
   UPDATE briefing_sessions       SET user_id = SYSTEM_DEFAULT_USER_ID WHERE user_id IS NULL;
   ```
   All data is preserved. No data is deleted.

3. After the UPDATE, all `user_id` columns are non-NULL.
   Columns can then be altered to `NOT NULL` in a subsequent migration (Phase 16.1).

**SYSTEM_DEFAULT_USER_ID** is a fixed constant (e.g. `00000000-0000-0000-0000-000000000001`),
committed to the codebase and used consistently. It is never surfaced to end users.

### 5.3 Phase 16.1 — Data claim on first sign-up

When the **first real user** completes sign-up and onboarding:

1. During the onboarding "Import your watchlist" step, the frontend offers:
   > "We found an existing watchlist with N tickers. Import it to your account?"

2. On acceptance, a `claim_system_data(new_user_id)` function runs:
   ```sql
   UPDATE watched_tickers
      SET user_id = :new_user_id
    WHERE user_id = SYSTEM_DEFAULT_USER_ID;

   UPDATE portfolios
      SET user_id = :new_user_id
    WHERE user_id = SYSTEM_DEFAULT_USER_ID;

   UPDATE user_delivery_prefs
      SET user_id = :new_user_id
    WHERE user_id = SYSTEM_DEFAULT_USER_ID;
   ```
   `thesis_versions`, `memory_entries`, and `briefing_sessions` are NOT re-claimed
   — historical analysis records stay on SYSTEM_DEFAULT_USER as an audit trail.

3. The claim operation is **one-time**: after the first user claims, SYSTEM_DEFAULT_USER
   has no more watchlist/portfolio rows. Subsequent sign-ups start fresh.

4. If the user declines the import, SYSTEM_DEFAULT_USER retains the rows. An admin
   endpoint allows manual re-assignment.

**Risk:** If two users sign up simultaneously before either claims, the second claim
attempt finds 0 rows (already claimed). The UI shows "No existing data to import"
rather than an error. A DB-level `claimed_at` timestamp on the system user row
prevents race conditions.

### 5.4 Phase 16.2 — Backfill & cleanup

After a defined soak period (suggested: 30 days after Phase 16 launch):

1. Verify `SELECT COUNT(*) FROM watched_tickers WHERE user_id = SYSTEM_DEFAULT_USER_ID`
   returns 0 (all data claimed or acknowledged as unclaimed).
2. Archive SYSTEM_DEFAULT_USER rows to `_archive` tables or mark inactive.
3. Add `NOT NULL` constraints to `user_id` columns via migration.
4. Remove SYSTEM_DEFAULT_USER from `users` table (or set `is_active = FALSE`).

Step 3 (NOT NULL enforcement) is the only structural schema change. All prior
migrations were additive; this is the first constraint-adding migration.

### 5.5 Default ownership for new entities post-Phase 16

After Phase 16.0 deploys, any new row written by an authenticated request MUST
include `user_id = request.state.user_id`. Services that currently write NULL
(e.g. `watchlist_repo.ticker_add`) are updated to accept `user_id` as a parameter.
Services called by the background loop (scheduled jobs) write with
`user_id = SYSTEM_DEFAULT_USER_ID` or the target user's ID from the job payload.

## 6. Security Model

### 6.1 API protection

**Middleware chain (FastAPI dependency injection):**

```
Request
  → CORS check
  → extract_token(request) → Optional[str]
  → verify_jwt(token) → UserIdentity | 401
  → inject request.state.user_id
  → route handler
```

`verify_jwt` validates the token signature against Supabase's JWKS endpoint
(cached in memory with a 1-hour TTL). It checks `exp`, `aud`, and `iss`. No
database call is made per-request; JWT verification is purely cryptographic.

The JWKS URL and JWT secret are environment variables (`SUPABASE_URL`,
`SUPABASE_ANON_KEY`). They are never logged or returned in API responses.

**Unauthenticated requests to protected routes** receive HTTP 401 with body:
```json
{"detail": "Authentication required"}
```
No information about the route's existence or resource shape is revealed.

**Wrong user accessing another user's resource** receives HTTP 403:
```json
{"detail": "Not authorized"}
```
No resource ID or existence is confirmed in the error.

### 6.2 Password handling

ClearSignal does not store passwords. Magic link and OAuth are the only sign-in
methods. There is no password hash, salt, or bcrypt in the application layer.
Supabase Auth manages any credential storage internally with bcrypt + pepper if
email/password is ever added as a fallback.

**Benefit:** The entire class of password storage vulnerabilities (weak hashing,
rainbow table attacks, credential stuffing amplification) is eliminated.

### 6.3 Account recovery

**Magic link:** Recovery is inherent — a new magic link is a de facto "forgot password."
A user who loses access to their email account contacts support; there is no
self-service recovery path beyond email access.

**Google OAuth:** Recovery follows Google's account recovery. ClearSignal has no
recovery lever for users locked out of their Google account.

**Account deletion:** GDPR-compliant deletion flow:
1. User requests deletion via settings
2. 14-day cool-down period (reversible)
3. On confirmation: user_id rows in all tables soft-deleted → `is_active = FALSE`
4. After 30 days: hard delete (or anonymize) personal data
5. Analysis results (thesis, memory) are anonymized (user_id nulled) rather than deleted
   — company intelligence is platform-level and must be retained

### 6.4 Session model detail

```
Access token
  Type:    JWT (HS256 or RS256, Supabase-issued)
  TTL:     1 hour
  Storage: JavaScript memory (never localStorage, never sessionStorage)
  Scope:   All authenticated API calls

Refresh token
  Type:    Opaque string (Supabase-issued)
  TTL:     30 days sliding (reset on each use)
  Storage: httpOnly Secure SameSite=Strict cookie
  Scope:   /auth/token/refresh only

Session invalidation
  - Explicit logout: refresh token revoked server-side via Supabase signOut()
  - Password change (if added later): all sessions invalidated
  - Account suspension: all active refresh tokens revoked by admin
```

### 6.5 Rate limiting

Protected endpoints are rate-limited at the reverse proxy (Render / nginx) layer:

| Endpoint class | Limit |
|---|---|
| `/auth/*` (magic link requests) | 5 req/min per IP |
| `/analyze`, `/ask` | 20 req/min per user_id |
| `/admin/*` | 30 req/min per user_id |
| All other authenticated | 120 req/min per user_id |

Rate limits are enforced before JWT verification to prevent token farming at the
auth endpoints.

### 6.6 Audit trail

Every mutating request (POST, PUT, DELETE, PATCH) on user-scoped resources appends
a row to an `audit_log` table:

```
audit_log
├── id           VARCHAR(36) PK
├── user_id      VARCHAR(36) NOT NULL  FK → users.id
├── resource     VARCHAR(60)           -- 'portfolio' | 'watchlist' | 'prefs' | ...
├── resource_id  VARCHAR(36)
├── action       VARCHAR(20)           -- 'create' | 'update' | 'delete'
├── ip_address   VARCHAR(45)           -- IPv4 or IPv6
├── user_agent   VARCHAR(500)
└── created_at   TIMESTAMPTZ NOT NULL
```

Audit log rows are never deleted (append-only). The table is write-once from the
application layer; only DB-level admin roles can read or archive it. This supports
future compliance requirements (SOC 2, FINRA record-keeping) without redesign.

## 7. User Experience

### 7.1 Sign-up flow

```
Landing page
  → [Sign up free] button
  → Email input screen
      User enters email
      → POST /auth/magic-link
      → "Check your inbox" confirmation screen
  → User clicks link in email
      → Supabase validates OTP
      → JWT issued
      → Redirect to /onboarding

Onboarding wizard (4 steps, can skip any)
  Step 1: Profile  (display name, timezone)
  Step 2: Watchlist  (import from system data if available, or add tickers manually)
  Step 3: Portfolio  (create first portfolio — blank or clone from watchlist)
  Step 4: Briefing   (confirm daily briefing time and channel preference)
  → /dashboard
```

### 7.2 First portfolio flow

At onboarding Step 3, the user is shown:

> **Your first portfolio**
> Start with your watchlist tickers or add positions manually.
>
> [Import from watchlist] [Start blank] [Skip for now]

"Import from watchlist" creates a portfolio with all watchlist tickers as
`membership_class = 'watchlist'`, with `weight = NULL` (no weights required).
This mirrors the existing `portfolio_mirror_service` behavior.

The portfolio is named "My Portfolio" by default. It is set as `is_default = TRUE`.

### 7.3 First briefing flow

At Step 4, the user sets:
- Delivery time (default: 08:00 in their timezone)
- Channel (default: in-app)
- Frequency (default: daily)

The first morning brief fires the following morning. If the user skips Step 4,
defaults are applied from `user_settings` and the briefing fires anyway.

### 7.4 Return sign-in flow

```
Dashboard (session expired or first visit)
  → "Sign in" → email input
  → Magic link sent (or Google OAuth button)
  → Session restored → /dashboard (previous state preserved)
```

There is no persistent "remember me" toggle — the 30-day refresh token is always set.
This matches the expected behaviour for a professional tool used regularly.

## 8. Future Compatibility

### 8.1 Stripe billing

The `users` table is designed to accept a Stripe customer ID with a zero-migration
addition:

```sql
ALTER TABLE users ADD COLUMN stripe_customer_id VARCHAR(32) UNIQUE DEFAULT NULL;
```

Plan gating is enforced at the route level using a `require_plan(min_plan)` dependency
that checks a `users.plan` column (also additive). No architectural change is needed.

Suggested plan structure (designed, not built in Phase 16):

| Plan | Target | Key limits |
|---|---|---|
| Free | Individuals | 5 tickers, 1 portfolio, weekly briefing |
| Pro | Active investors | Unlimited tickers, 3 portfolios, daily briefing |
| Teams | Small funds | Shared watchlists, team-level insights |
| Institutional | RIAs / funds | API access, custom delivery, SSO |

### 8.2 Teams

The data model supports teams with one additive migration:

```
organizations
├── id           VARCHAR(36) PK
├── name         VARCHAR(200) NOT NULL
├── plan         VARCHAR(20)  DEFAULT 'teams'
└── created_at   TIMESTAMPTZ NOT NULL

organization_members
├── org_id       VARCHAR(36) FK → organizations.id
├── user_id      VARCHAR(36) FK → users.id
├── role         VARCHAR(20)   -- 'owner' | 'admin' | 'member' | 'viewer'
└── joined_at    TIMESTAMPTZ NOT NULL
```

Shared portfolios add `org_id` to the `portfolios` table:
```sql
ALTER TABLE portfolios ADD COLUMN org_id VARCHAR(36) DEFAULT NULL
    REFERENCES organizations(id);
```

Authorization is extended: a portfolio is accessible if
`portfolio.user_id = request.user_id` OR
`portfolio.org_id IN (SELECT org_id FROM organization_members WHERE user_id = request.user_id)`.

### 8.3 Institutional accounts

Institutional accounts require:
1. **SAML/SSO** — Supabase Auth supports SAML 2.0; no application code changes
2. **API keys** — service accounts for programmatic access (not user sessions)
3. **Audit export** — the `audit_log` table is already structured for SOC 2 export
4. **Data residency** — Supabase supports region selection; no schema changes

These are Phase 16.3+ concerns. The identity model does not need to change.

### 8.4 Investment Jarvis roadmap compatibility

The Jarvis architecture (AI agent with persistent memory per user) maps cleanly
to the existing `memory_entries` table once `user_id` is non-nullable:

- Each user's `memory_entries` is their Jarvis context
- `ticker_memory` becomes user-scoped with `user_id`
- `personalized_insights` is already user_id-aware

No new tables needed for Jarvis identity integration. The agent simply filters
all memory queries by `user_id = request.state.user_id`.

## 9. Rollout Plan

### Phase 16.0 — Foundation (no user-visible change)

1. Add `users`, `user_profiles`, `user_settings` tables via migration
2. Add `audit_log` table
3. Seed SYSTEM_DEFAULT_USER
4. Run NULL → SYSTEM_DEFAULT_USER backfill SQL (idempotent on repeat runs)
5. Deploy Supabase Auth project; configure magic link + Google OAuth
6. Add `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_JWT_SECRET` to env
7. Add JWT middleware (bypassed by default — `AUTH_ENABLED=false`)
8. Deploy and verify `/admin/portfolio-status` still passes (`safe_state=true`)
9. Confirm `db_table_count >= 34` (3 new tables)

**Gate:** 0 regressions in `tests/test_services/`. Middleware in bypass mode.

### Phase 16.1 — Auth wire-up (internal users only)

1. Set `AUTH_ENABLED=true` in staging / internal environment
2. Sign up first real user; verify data claim works
3. Test all portfolio, watchlist, and delivery flows under authenticated context
4. Run `validate_16_auth_shadow.py` (new validation script)
5. Verify zero data visible to unauthenticated requests on protected routes

**Gate:** Auth bypass for production still in place. All internal tests pass.

### Phase 16.2 — Production auth enabled

1. Enable `AUTH_ENABLED=true` in production
2. Update frontend to send Bearer token on all API calls
3. Add onboarding wizard to frontend
4. Monitor for 401 errors from existing sessions (should be zero — no existing sessions)
5. Monitor `audit_log` for unexpected mutation attempts

**Gate:** Zero authentication errors on protected routes for 48 hours.

### Phase 16.3 — NOT NULL enforcement

1. Verify SYSTEM_DEFAULT_USER has 0 watchlist/portfolio rows (all claimed or expired)
2. Apply NOT NULL migration to `user_id` columns
3. Remove AUTH_ENABLED bypass — auth is now always required on protected routes

## 10. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Data claim race condition (two users sign up simultaneously) | Low | Medium | DB-level `claimed_by` column with UPDATE ... WHERE claimed_by IS NULL; idempotent claim |
| Supabase Auth outage prevents sign-in | Low | High | Fall-through to session cookie (refresh token in cookie still works during Supabase partial outages); monitor Supabase status page |
| JWT JWKS cache stale during key rotation | Low | Medium | JWKS cached with 1h TTL; Supabase rotates keys with 24h overlap; no window of failure |
| Email deliverability for magic links | Medium | High | Configure custom domain in Resend/SendGrid; monitor bounce rates; Google OAuth as fallback |
| SYSTEM_DEFAULT_USER data not claimed (user skips onboarding) | Medium | Low | Admin endpoint to manually assign; 30-day claim window before archival |
| Session token storage in memory lost on tab close | High | Low | Expected UX trade-off for security; refresh token cookie restores session in < 1s |
| OAuth scope creep (Google requesting more than email) | Low | Medium | Request minimum scope: `email`, `profile` only; no Google Drive / Calendar |
| `user_id NOT NULL` migration breaks legacy NULL rows | Low | High | Phase 16.0 backfill runs first; 30-day soak before NOT NULL; verified in staging |
| Regulatory: user data retention under GDPR/FINRA | Medium | High | Deletion flow designed with 14-day cool-down + anonymization; `audit_log` retained; legal review before Phase 16.2 |
| Teams feature requiring portfolio sharing across users | Future | Medium | `org_id` FK designed into portfolios; no schema rework needed |
